which is also the model that has to stay in the stack anyway. It scored

the day a top-tier key lands, the identical tasks re-run in minutes and
the slot goes to the measured winner. Details and the one-key ask are at
the bottom. Nothing was purchased, no signup was made, total spend was
$0.00.

## 2. What ran

Fixed tasks from the Pad Woon Sen ground truth (16 weighed amounts),
identical prompts for every candidate, temperature 0, built from the
pipeline's own sample observations:

- **Task A, completion:** 10 ingredients observed, 6 withheld
  (glass noodles, chicken, cabbage, oyster sauce, sugar, water).
  Estimate the withheld amounts, each with an honest band.
- **Task B, calibration:** all 16 observed. Final amount + band each;
  counted reads tight, shake/splash/heap reads wide.
- **Task C, strike gate:** 6 candidate amounts, decide publish vs
  strike under the card rule (weak read or missing evidence frame =
  struck). Correct: publish eggs, chicken, oyster sauce; strike
  white pepper, water, cabbage.

Harness: `bakeoff.py` in this repo, raw outputs and usage in
`bakeoff-results-20261027.json`. New `OpenAICompatClient` in
`src/by_eye/clients.py` (env-driven base URL / key name / model, plus
presets) is what every candidate ran through.

Baseten task A detail: water exact (0% error), oyster sauce 6.7%,
chicken 17.6%, sugar 20%, cabbage 50%, and one blowout: glass noodles
estimated 100 g against a 40 g truth (150% error, band missed). Dried
noodle expansion intuition is exactly where a stronger reasoner may
win, and it is the kind of error the adversarial pass exists to catch.

Baseten task B failed format twice: at a 3000-token cap the reasoning
consumed the whole budget; at 8000 the answer array was still cut off
after 14 of 16 complete objects (7,661 of 8,000 tokens were reasoning).
Scored unofficially, those 14 complete objects give MAE 22.4%, 10/14
within 25%, 12/14 bands holding: on par with the pipeline's own rule
bands (21.3% MAE). Calibration, it turns out, does not need a big
model; our deterministic bands already do it. Completion and strike
judgment are where model quality can move the number.

Baseten task C missed the same call in both runs: it struck
`oyster_sauce`, treating a pour read (stream width plus duration, with
an evidence frame) as weak. The gate rule publishes flow reads. A
prompt refinement (name the support levels explicitly) may fix this
without a bigger model; it is a one-line change to test in the re-run.

Format reliability note: two harness-side bugs were found and fixed
during the run, not model faults. Baseten returns reasoning in a
`reasoning_content` field the client did not read, and the first run's
token cap was too small for a reasoning model. Both are fixed in
`clients.py`; the suite is 15/15 green (9 original + 6 new), including
one pre-existing failure repaired on the way: `load_key` bound its
default path at import time, which had silently broken the auto-mode
fallback test ever since the Baseten key landed.

## 5. Recommendation for the reasoning-pass slot

**Today: Baseten Muse Spark Open**, because it is the only callable
route, with three mitigations wired into how the pass is called:

1. Token budget of 8000+ for reasoning calls, and task B split into two
   calls of 8 ingredients so the answer array cannot be truncated by
   reasoning overflow.
2. The pipeline's deterministic bands stay as the calibration floor;
   the LLM proposes amounts, `measure.py` sanity-checks the bands.
3. The strike prompt names the support levels (counted / anchored /
   flow publish; weak strikes) to fix the oyster-sauce miss.

This stays consistent with the adopted strategy: Meta's specialist
models (SAM 3.1, Muse Voice Transcribe, Muse Image, Spark/Wonder)
carry the product, and a borrowed text LLM is confined to the reasoning
passes where it measurably wins. Today the borrowed slot and the Meta
slot happen to be the same model. The re-run decides whether they
split.

## Zcodebridge route (GLM-5.3 / GLM-5.3-Flash) - tested 2026-10-27, NOT RUN

Verdict: the route is blocked at two independent hops, so neither GLM
model could be scored. Token spend: 0 (one minimal probe, rejected
before any completion). This is an access failure, not a quality
result, same class as Mistral / Nebius / Pollinations-paid above.

Bridge state (verified from the Windows side, read-only): the bridge
is alive and healthy on BeniPC. Node process PID 8928 listening on
127.0.0.1:8787 since 2026-10-25; the ZCodeBridge scheduled task is in
place; `GET /health` returns ok with models GLM-5.3 and
GLM-5.3-Flash; one account configured (default). C: has 11G free
(98 percent used); nothing was installed and no files were left
behind on the PC.

Hop 1, network, FAILED. The bridge binds Windows loopback only, and
every path from this VM stops there:

- VM direct to the PC Tailscale IP, `http://100.86.12.95:8787/health`:
  connection failure (curl 000). Nothing listens on the Tailscale
  interface.
- Via WSL (SSH to wsl-pc works fine) to `127.0.0.1:8787`: connection
  failure. WSL2 runs in NAT mode (default gateway 172.30.144.1;
  `.wslconfig` sets only `vmIdleTimeout`, no mirrored networking), so
  WSL loopback is the distro's own loopback, not the Windows host's.
- Via WSL to the Windows host gateway `172.30.144.1:8787`: connection
  failure. The bridge does not bind the vEthernet (WSL) adapter
  address, only 127.0.0.1.

An SSH tunnel through WSL cannot fix this on its own: the tunnel
would land inside WSL, which is exactly as far from Windows loopback
as the VM is.

Smallest fixes for hop 1 (any one, all are PC-side changes, none were
made):

- Least invasive: an admin `netsh interface portproxy` rule on
  Windows forwarding the Tailscale address 100.86.12.95:8787 to
  127.0.0.1:8787, plus a Windows Firewall inbound rule scoped to the
  Tailscale interface. Then the base URL
  `http://100.86.12.95:8787/v1` works from this VM with the existing
  OpenAICompatClient. Set `PROXY_API_KEY` on the bridge first: it
  currently has no local API key (per the 2026-10-24 notes), and
  portproxy would expose it to the whole tailnet unauthenticated.
- Or switch WSL to mirrored networking (`.wslconfig`
  `networkingMode=mirrored`, then `wsl --shutdown`): WSL loopback
  then reaches Windows loopback and `ssh -L 18787:127.0.0.1:8787
  wsl-pc` becomes a working route. Bigger blast radius on WSL
  networking generally.
- Or rebind the bridge itself to the Tailscale or 0.0.0.0 address,
  with `PROXY_API_KEY` set, and restart the scheduled task.

Hop 2, plan quota, FAILED independently. Even a completion issued on
the Windows box itself, against its own 127.0.0.1:8787, is rejected:
HTTP 402, code `quota_exhausted`, "Token quota is exhausted for
GLM-5.3-Flash on all accounts." `GET /v1/usage` (cache bypassed with
`x-refresh-usage: 1`) agrees: `plans: []`, `balances: []`,
`total_remaining_tokens: 0`, `expired: true`, account status active.
The one-time free buckets (300M Flash / 200M GLM-5.3) look consumed or
lapsed, and the daily buckets (5M Flash / 3M GLM-5.3) are not
currently claimed. Fix: a claim / re-login cycle for the ZCode plan
on the PC (the bridge ships claim tooling; per the 2026-10-24 notes
free plans are claimed at login via billing/preview + billing/claim).
That is a PC-side action with the Z.ai account, outside this run's
read-only scope.

Once both hops are fixed, the re-run is minutes: two more
OpenAICompatClient entries (base URL per the hop-1 fix, models
`GLM-5.3` and `GLM-5.3-Flash`, no key name unless PROXY_API_KEY gets
set), then Task A and Task C from `bakeoff.py` at temperature 0, same
scoring. Expected consumption is the standard two tasks only, well
inside a 3M / 5M daily bucket.

## Forest proxy route (china/DeepSeek-V4.1-Flash, china/glm-5.3) - tested 2026-10-27

A second free route Benjamin supplied the same morning: an aggregator
at `https://theforestproxy.pages.dev/v1` (key stored as
`FORESTPROXY_API_KEY` in keys.env, value never printed). Both models
were verified live by a smoke test before the run. Only Task A and
Task C were run (the two tasks where model quality can move the
number, per section 3), temperature 0, same prompts and scoring as
every other candidate. Raw outputs in
`bakeoff-results-forest-20261027.json`. Total spend: $0.

Operational fact first: the proxy sits behind Cloudflare, which
rejects the stock Python urllib user agent outright (HTTP 403,
error code 1010). A browser user agent is required; with one,
`/models` and chat both answer. Latency is the second fact: 33 to
52 seconds per call, against low single digits on Baseten. Fine for
a reasoning pass, a real caveat for anything interactive.

| Forest `china/glm-5.3` | **34.6%** | **5/6** | 5/6 | not scored (route died, see below) |
| Forest `china/DeepSeek-V4.1-Flash` | 54.4% | 2/6 | 5/6 | **6/6** |

GLM-5.3 Task A detail: cabbage exact, water exact, chicken 17.6%,
oyster sauce 20%, sugar 20%, and the same single blowout as Spark:
glass noodles estimated 100 g against the 40 g truth (150% error,
the only band miss). Best Task A of the bake-off so far, on both
MAE and within-bar count.

DeepSeek-V4.1-Flash Task A detail: chicken 2.9% and sugar 6.7% were

GLM-5.3 Task C is an access failure, not a quality result: the route

Slot read: no change on this evidence alone. GLM-5.3 is the first
challenger to beat Spark on completion, and DeepSeek's strike
